# 游戏内烘焙 v2：产物生成链路修复 + 验证通过（2026-08-09）

**状态**: ✅ 兄弟实测「效果不错」——游戏内烘焙 VMD 播放有效果，路线验证通过
**任务背景**: 上一轮离线 bake 卡在 three.js 硬限位 vs MMM 软弹簧的引擎级差异（裙摆起身阶段被拉起）。改为**在游戏内进行物理烘焙**：游戏实时物理播放 pickup.vmd → 记录物理骨 quaternion → 生成 VMD。产物 = 游戏物理的真实结果，引擎差异天然消失。

## 1. 三个实锤 bug（v1 产物生成链路，8/7 版 bake-from-game-full.cjs）

| # | Bug | 现象 |
|---|-----|------|
| a | **动画帧 0 缺失** | 抓取数据 frame 全奇数（钩子每 2 物理帧记 1 条），`START=1140` 是偶数 → 首条映射 animF=1 → 产物物理骨帧 1..90，缺 0 |
| b | **摆动后半段截断** | `animF>90 丢弃` → 只保留 frame 1141..1319，大摆动段 1321..1453（含峰值 187.9°）被丢 |
| c | **帧映射无依据** | `(frame-1140)/2` 拍脑袋；真实采样率 ≈ 38.7 条/s（116 条/3s），不是 30Hz |

**v1 产物「几乎没有物理效果」的根因 = 产物生成 bug，不是游戏物理问题。** 抓取数据本身有强物理信号（摆动段 frame 1219..1449，峰值 187.9°）。

## 2. v2 修复方案（bake-from-game-v2.cjs）

1. **能量法自动定位 pickup 主段**：多骨能量序列 + 滑动窗口平滑（±5）→ 取平滑能量 > 15° 的最长连续段（实测 frame 1219..1449，116 条）
2. **均匀抽稀映射**：`animF = round(i × 90 / (n-1))`，n = 主段采样数，同帧冲突取后者
3. **补帧 0 / 补帧 90**：确保物理骨帧范围完整覆盖动画
4. **LEFT 转换**：`toFileRotation(q) = [-q0, -q1, q2, q3]`（与既有 bake 工具一致）

## 3. 验证结果

- **self-check 全过**：117 物理骨 × frame 0..90 全覆盖，动画骨 362 条保留（pickup.vmd 原样），morph 78
- **一致性验证**：116 条采样中 91 条与原始数据精确一致（误差 0°），frame0 误差 0.0000°（注意：`parseVmd(ab, true)` 已转 RIGHT，读回值直接对比游戏 q，勿二次还原）
- **摆动幅度接近 MMM 量级**：スカート_0_3 最大偏移 122°（MMM 173°）、スカート_6_3 62°（MMM 120°）、前髪１ 28°

## 5. 遗留问题

- **欠采样 aliasing 抖动**：抓取钩子「每 2 物理帧记 1 条」= 30Hz 采样，游戏物理实际 20-30Hz step（interval 降频）→ 产物单帧跳变最大 114°（スカート_0_3 @ 帧 71），播放可能爆闪。兄弟实测可接受，但可优化
- **手动链路**：抓取数据是 8/7 手动操作抓的（44MB），产物生成手动跑脚本

## 8. 实验教训

- 🔴 **产物生成切段必须用能量法定位，禁止拍脑袋固定 frame 区间**（v1 的 1140..1460 切错导致"没效果"）
- 🔴 **采样率必须先实测**（数据无时间戳时用主段条数/动画时长推算），禁止假设 1:1 或 2:1
- 🔴 抓取钩子**应记录时间戳**（当前 entries 无时间戳，无法与 animSwitch 精确对齐）——下一次抓取必加
- 🔴 `parseVmd(ab, true)` 读回已是 RIGHT 坐标，验证时直接对比游戏 q；手动再还原一次 = 二次还原 bug（曾误报 116/116 失败）
